# DuckDB security and GeoPackage evidence inventory

**Task:** Plan 14, task 14.1.2
**Inventory date:** 2026-11-22
**Scope:** Baseline mapping of existing policy claims to the current implementation and tests. This is not a direct-engine security probe, complete bypass assessment, loader revalidation, or production-readiness verdict.

## Evidence labels and boundary

- **Engine/config-enforced:** behavior configured in DuckDB or its client configuration; the named tests below generally observe the executor path, not an independent bypass of its SQL gate.
- **Classifier-enforced:** request SQL rejected by the executor's restrictive `validate_statement` string classifier before DuckDB prepares it.
- **Loader-enforced:** private Rust-side GeoPackage checks, separate from the request SQL classifier.
- **Tested observation:** a finite test or prior probe observed the behavior; it does not establish an exhaustive guarantee.
- **Unverified:** no relevant evidence in the scoped implementation/tests and prior report reviewed here.

`docs/security/duckdb-execution-policy.md` correctly notes that DuckDB is not reachable from HTTP and that SQLite remains the default. The implementation is feature-gated qualification code. Conclusions below must not be generalized into request-path security or exhaustive engine guarantees.

## Discrepancies, open questions, and claims not to make

1. The policy document calls several controls “tested” but its contract tests invoke the executor and therefore combine classifier behavior with connection configuration. In particular, INSTALL/LOAD/SET and non-SELECT write denials are classifier outcomes, not proof that DuckDB itself rejects the operation.
2. The file/URL SELECT tests are more informative about configured external access because SELECT passes the classifier, but they are still a small set of observations and do not establish all DuckDB functions, extension paths, or engine bypass behavior. Task 14.2.1 is the direct-Connection probe task for this gap.
3. `validate_statement` is deliberately string-based. Existing tests establish selected denials and allowed temp-table behavior only; they do not prove grammar completeness or bypass resistance. Do not call it an SQL parser, authorizer, or exhaustive security boundary.
4. Prior `allowed_paths` plus `ST_Read` observations contradict any claim that this setting safely confines DuckDB Spatial file access. Do not rely on it as authorization. The current private loader does not use `ST_Read`.
5. `TrustedGeoPackagePath` provides an internal capability after canonicalization, but the task evidence does not identify a production caller or deployment-controlled authorization/provisioning lifecycle. Do not claim caller trust or request isolation is established end to end.
6. The synthetic loader tests establish selected metadata, SRID, dimensional, empty/NULL, and WKB behavior. They do not establish comprehensive malformed-file robustness, topology validity, resource limits, or behavior against every SQLite/GeoPackage adversarial input.
7. Fresh in-memory connections and transaction rollback support request/batch isolation claims only within exercised executor lifecycles. Do not claim future-drop cancellation, process-crash rollback, or bounded cleanup without the relevant lifecycle evidence.
8. No DuckDB production limits for memory, threads, concurrency, temp storage, input, rows, value size, or serialized output are established here. Do not copy SQLite policy thresholds or Plan 8 experimental settings as DuckDB caps.
9. This baseline does not determine whether a control can be made sufficient, whether a process sandbox is required, or whether a later integration is a go/no-go. Those conclusions require the later prescribed probes, research, and synthesis.
