- Current seam facts: `rewrite_node` rejects all six method names unconditionally via `unsupported_geography_method` before any argument inspection, so arity/NULL claims today are rejection semantics only; expression shape cannot prove runtime SRID, dimension, extent, validity, or FullGlobe status. Any future support must add per-value runtime enforcement, not just AST checks.
- Prior evidence (DuckDB engine v2.0.0, client `duckdb = "=1.20000.2"`, Spatial ext `a3dbcd1781`, SHA-256 `8ec99d87…a8d0bc`): ordinary `ST_*` operations are planar; `ST_Buffer` distance follows coordinate units; CRS mismatch raises a bind error instead of SQL Server's NULL; `ST_Area_Spheroid` is a distinct WGS84-oriented operation; community S2 `s2_contains` returned `true` for a polygon vertex where SQL Server documents boundary `0`, `s2_within` was absent from the installed binary, `s2_area` is perfect-sphere square meters, and no S2 buffer exists. None of these establish SQL Server parity.
- Plan 9/G12 facts: SpatiaLite's ellipsoidal area is RTTOPO/PROJ-based, not SQL Server parity, and its cross-equator case emitted `RTTOPO error: ptarray_area_spheroid: cannot handle ptarray that crosses equator`; there is no SQL Server runtime oracle in this project. Numeric equality with SQL Server therefore cannot be demonstrated, only documented-contract conformance plus deterministic bounded behavior.
- No planar or approximate operation may be presented as geography-compatible; a bounded subset is admissible only with runtime-enforced guards and tests that establish SQL Server semantics. Verdicts must default to explicit no-go when enforcement or evidence is missing.
- Dependency rule: research and propose only. Adding any crate (e.g. GeographicLib/S2 bindings) requires separate explicit user approval; the report must not assume or rely on one.
- Acceptance check must be run literally as `git diff --check`; the orchestrator owns full/wave suites and the final acceptance gate.
- Verification retry after review: the `STArea` axis-order ambiguity and the `STContains`/`STWithin` boundary-rule wording were corrected in the report; see the follow-up correction commit and the `STATE_13.md` note.
