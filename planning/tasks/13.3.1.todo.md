## Notes

- G37 §1 and §6.1–6.2 make both methods explicit no-go: DuckDB documents `ST_Contains` as true for a boundary point, and no inspected SQL Server page states the boundary rule; planar and S2 (spherical) edges are not ellipsoidal geodesics. Bound domain = empty, so no accepted fixtures exist and no planar/S2 substitution may be introduced.
- Rejection is currently arity/receiver independent (`rewrite_node` arm before argument inspection), so the only code change is the predicate-specific reason; the asserted prefix must stay intact for `tests/spatial_methods_contract.rs` and the G37 §3 anchor.
- `Expression::MethodCall` handling is at `src/transpiler/spatial.rs` ~1032 and `unsupported_geography_method` ~1124; `tests/spatial_methods_contract.rs` skips without `SDA_TEST_SPATIALITE`, so the literal acceptance command proves little by itself — the configured run is the real guard.
- DuckDB functions used by the new test are limited to behavior already recorded in G33-2 (`ST_Contains`, `ST_Within`, `ST_GeomFromText`, `ST_SetCRS`), the documented spheroid point-pair primitives (`ST_Distance_Spheroid`, `ST_DWithin_Spheroid`), and the loaded-artifact identity guard; `ST_SRID`/`spatial_version()` are known absent and must not be used. `sha256sum` is a Linux-only test-side check, not a dependency.
- Exact compatibility bar: a local projection could be a candidate only with rigorous error bounds plus runtime guards proving exact results on a bounded domain; a caveated approximation alone remains rejected. This task attempts no such projection. The spheroid point-pair observation is descriptive evidence that these primitives exist and behave as documented; it is not a containment transformation and must not be presented as one.
- Artifact identity is established by the pinned SHA-256 and, when available, observed extension metadata; the absence of a particular function name is never treated as proof of what the artifact or SQL Server does.
- Test expectations for DuckDB boundary inclusivity follow the documented behavior cited in G37 §6.1; if the pinned binary returns otherwise, record the observed deviation and stop for orchestrator review rather than weakening the no-go.
- Do not touch `src/routes.rs`, config/runtime selection, other geography methods, SQLite executor/security, response shape, `Cargo.lock`, or anything outside the task file scope; no network, no request-time extension work, no final resource-limit values.

## Discovered (scope check, read-only)

- Community `geography` (paleolimbot/duckdb-geography) exposes no spheroidal/geodesic predicate: the complete function reference lists `s2_contains`, `s2_within`, `s2_cell_contains` (S2 cell, not geography), `s2_dwithin`, `s2_intersects`; every metric (`s2_area`, `s2_perimeter`, `s2_length`, `s2_distance`) is documented as sphere-based ("perfect sphere" / S2 earth radius). Source registration confirms `s2_contains`/`s2_within` call `S2GEOGRAPHY_OP_CONTAINS`/`S2GEOGRAPHY_OP_WITHIN` in `src/s2_binary_index_ops.cpp`.
- Official Spatial 2.0 exposes ellipsoidal measurement/proximity only: `ST_Area_Spheroid`, `ST_Length_Spheroid`, `ST_Perimeter_Spheroid`, `ST_Distance_Spheroid` (POINT_2D pair), `ST_DWithin_Spheroid` (POINT_2D pair). There is no `ST_Contains_Spheroid`/`ST_Within_Spheroid`; `ST_Contains`/`ST_Within` are planar and `ST_Contains` is documented as boundary-inclusive.
- Whether `ST_DWithin_Spheroid` can be combined with a nearest-boundary construction into exact point-in-polygon geography semantics remains unresolved and is not claimed: no exposed geodesic nearest-point-on-boundary operation exists, and planar nearest-point/`ST_ShortestLine` would not establish the geodesic boundary. Orchestrator direction now recorded in the G37 report and the EXECUTION_PLAN_13 task spec: community `geography` is S2/sphere and official Spatial spheroidal functions are point-pair measurement/proximity primitives, not established containment replacements. The revised plan adds step 7 as a descriptive point-pair observation only; the explicit-rejection decision is unchanged.
