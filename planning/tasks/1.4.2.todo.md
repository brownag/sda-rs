# Task 1.4.2 Micro-plan — Optional spatial capability and GeoPackage metadata

## Goal
Initialize optional spatial support for each request-local SQLite connection and expose discovered/overridden GeoPackage geometry metadata through the existing route seam.

## Context and constraints
- Branch: `feature/sqlite-mvp`; planning artifacts are tracked separately.
- Dependencies 1.2.1 and configured-path executor are complete.
- Revised task specification authorized by commit `2ec35dc`.
- `Config` already exposes optional `spatial_extension` and `geometry_column`; route code currently does not pass them to execution.
- Authorized files: `src/spatial.rs`, `src/lib.rs` app/module state, `src/routes.rs`, `src/executor/mod.rs`, and `src/executor/sqlite.rs`.
- The orchestrator authorized `Cargo.toml`/`Cargo.lock` changes only to enable rusqlite's existing `load_extension` feature; do not add a new crate dependency.
- No transpiler/serializer changes and no AOI AST rewrites.
- Existing `target/` is untracked and must be left untouched.

## Tasks
1. Define `src/spatial.rs` types/API for per-connection capability initialization, optional GeoPackage metadata (table, geometry column, SRS ID), geometry-column override, and a structured error when spatial-required functionality is unavailable.
2. Register the spatial module and carry spatial extension/geometry override configuration through app state and routes into executor construction.
3. Initialize the capability on each request-local connection in the executor, without requiring spatial support for ordinary SQL. Expose the resulting capability and geometry metadata to the route/request result seam for downstream spatial work.
4. Add `spatial::` tests for ordinary SQLite without metadata, dynamic `gpkg_geometry_columns` discovery including SRID, configured override behavior, configured missing extension, and the structured spatial-required unavailable error.
5. Add route-request integration coverage proving extension/geometry configuration reaches per-request initialization and metadata/capability is exposed through the route seam; avoid requiring an installed extension for deterministic negative-path tests.
6. Run exactly `cargo test spatial::` and `cargo test routes::`. Record whether SpatiaLite is available; if available, smoke-test a real spatial function.

## Task 1.5.1 interface contract
Provide a per-request spatial capability/metadata value from executor initialization, with stable accessors for: spatial functions available/unavailable, optional discovered GeoPackage table/geometry-column/SRS metadata, and a structured `require_spatial` failure. A missing GeoPackage metadata table must remain distinct from unavailable spatial functions. Geometry override should select the effective geometry column without falsifying the discovered metadata. Keep this API independent of SQL transpilation; 1.5.1 can consume it when implementing AOI/UDF rewrites and error handling.
