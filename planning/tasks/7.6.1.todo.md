# Task 7.6.1 micro-TODO — Geography buffer, area, and text

## Read-only analysis and decisions

Task 7.4.1 establishes that the existing SpatiaLite functions do not provide
general SQL Server `geography` semantics:

- **`.STBuffer(distance)` — reject explicitly.** SpatiaLite `ST_Buffer` is a
  GEOS planar buffer whose units follow the geometry CRS; at SRID 4326, a
  distance of 1 was approximately one coordinate degree, not one meter. No
  supported geodesic implementation is established. Never emit
  `ST_Buffer(...)` as a geography substitute.
- **`.STArea()` — reject explicitly.** Bare `ST_Area` is planar coordinate
  area and demonstrably returned `1.0` for a 1-degree square at SRID 4326,
  unlike the geography's square-meter contract. The optional RTTOPO
  ellipsoidal operation is not established as SQL Server-compatible across
  SRIDs, geometries, empty/invalid inputs, and edge cases. Never emit planar
  `ST_Area(...)` as geography semantics.
- **`.STAsText()` — reject explicitly for now.** The feasibility report calls
  it conditionally implementable only for bounded ordinary 2D inputs and
  requires excluding Z/M and special geography cases. The current AST rewrite
  seam can see a geometry column or a constructor expression, but cannot
  safely prove the conditional contract for both:
  - GeoPackage metadata resolution supplies a column name and SRID, but the
    current rewrite representation does not carry a validated per-row
    dimensionality/empty/value constraint. Metadata z/m flags describe the
    declared column, not necessarily every stored BLOB's actual ordinates or
    all empty/NULL/value cases.
  - Constructor expressions can be arbitrary expressions or columns passed
    as WKT/SRID arguments; AST arity alone cannot establish ordinary 2D WKT,
    non-FullGlobe/non->hemisphere geography, valid input, or a supported SRID.
  - SQL NULL propagation and empty geometry output can be tested for a narrow
    execution case, but such tests do not enforce those constraints for all
    accepted calls. SQL Server geography's Z/M omission also differs from
    SpatiaLite's demonstrated retention.

  Therefore this task will not silently narrow acceptance to unverified
  ordinary examples or lower `.STAsText()` to `AsText`/`ST_AsText`. It will
  reject the instance method pending a separately approved, enforceable
  bounded contract. This is a discovered scope decision that conflicts with
  the feasibility report's conditional implementation classification; the
  report should be qualified to say conditional feasibility is not currently
  enforceable at this rewrite seam. The report is outside this task's
  must-edit scope (`src/transpiler/spatial.rs` and
  `docs/spatial-sql-contract.md`), so do not edit it; flag the report update
  for orchestration/approval.

The seam is centralized in `rewrite_node`: it already explicitly rejects
`.STContains`, `.STWithin`, and `.STIntersection`, then rewrites supported
constructors and `.STIntersects`. Unsupported instance methods are also
classified by `unsupported_geography_method`. Spatial expression detection
and traversal must be checked during implementation so these additions take
the same explicit validation path. Existing free-function spellings are not
CLR instance methods and must not be changed.
