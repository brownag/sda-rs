# 13.6.1 — Implement the internal DuckDB execution lifecycle (G38)

## Goal
Add an internal, `duckdb`-feature-gated DuckDB executor with request-local lifecycle and whole-batch failure semantics, without exposing it to HTTP requests or changing SQLite behavior.

## TODO items
- [x] Add a private DuckDB executor module and feature-gated internal API in `src/executor/mod.rs`; retain existing SQLite exports unchanged.
- [x] Implement fresh per-execution DuckDB connection and temporary state, synchronous execution on a Tokio blocking worker, and cleanup on success and failure.
- [x] Execute each statement batch as one transaction; explicitly roll back when execution fails, preserving both execution and rollback errors where applicable.
- [x] After plan approval, run a bounded, offline experiment against the exact pinned `duckdb = "=1.20000.2"` client API, using only existing local sources and synthetic in-memory SQL: verify whether its interrupt/deadline mechanism can cancel an executing query from another thread and whether it handles the preparation/execution race. Do not download/install dependencies or extensions.
- [x] If the experiment demonstrates a usable cancellation/deadline mechanism, implement it and add a deterministic cancellation/deadline contract test. Otherwise, add a reproducible test/report record containing the exact command and SQL/API sequence, observed behavior, and precise blocker; do not imply cancellation is enforced.
- [x] Add `tests/duckdb_execution_contract.rs` using synthetic/in-memory fixtures to verify successful temp-table workflow and isolation between independent executions.
- [x] Test that a failing later statement leaves no partial batch writes and that temporary state is cleaned up after success and failure.
- [x] Register the integration target in `Cargo.toml` with `required-features = ["duckdb"]`, if needed.

- [x] Run `git diff --check`; report any unresolved cancellation/deadline limitation as a blocker, without claiming production readiness.
