# Task 7.5.1 micro-TODO — Geography predicates and intersection

## Feasibility analysis

Task 7.4.1 classifies CLR instance methods `STContains`, `STWithin`, and
`STIntersection` as unsupported for general SQL Server `geography` parity.
SpatiaLite's similarly named operations are GEOS planar operations: the
configured probe found a mismatched-SRID `ST_Contains` result of `1`, unlike
SQL Server's documented `NULL`, and planar edges/overlay do not establish
round-earth semantics. Therefore this task will **not** lower any of these
methods to planar operations or claim compatibility. It will explicitly reject
these CLR instance-method spellings and document the unsupported boundary.

The existing `.STIntersects` path is a safe configured SpatiaLite operation
for satisfying the task's configured-runtime test requirement, but is not
evidence of geography parity. The contract test will execute it only as an
existing supported spatial operation, alongside rejection assertions for the
three unsupported methods. This avoids falsely implementing the infeasible
operations while still proving configured SpatiaLite initialization and query
execution.

The transpiler already recognizes method-call AST nodes and has centralized
`rewrite_node` handling; unsupported method calls currently risk passing
through unchanged. Add explicit rejection there and ensure spatial-method
detection causes these calls to take the validation path. Existing `.STIntersects`
semantics must remain unchanged. If inspection during implementation shows
these AST methods bypass that path or cannot be rejected without changing
unrelated/free-function behavior, stop and report the blocker rather than
broadening scope.
